# Learned Review Rules

> Hand-authored on 2026-04-26 from the lessons of the Datastar realignment build
> (`zing/realign-datastar-usage`).
> Source: ~700 lines of hand-rolled JS that reinvented framework-provided behavior,
> deleted across 41 build steps and 30 audit findings.
> These rules encode the *class* of mistake that produced that pile of JS in the
> first place. Review agents load this file during audits.

The web server uses **Datastar v1.0.0** (`templates/base.html`) as its declarative
reactivity layer. The browser side is intentionally thin: `base.js` (notification
opt-in) and `cc-modals.js` (iframe lifecycle + ClipboardItem write) — both
browser-API-only. Everything else lives in HTML attributes (`data-*`) and
server-side SSE patches. **The single largest source of bugs in this codebase
historically has been writing JavaScript to do work the framework already does.**
The rules below catch that class of mistake before it ships, regardless of the
specific symptom.

## Rules

### 1. Reinventing framework primitives in custom JavaScript

**Severity:** high

**Description:**
Code that uses `fetch()`/`addEventListener`/`document.querySelector(...).classList`
to do something Datastar already does declaratively is the recurring root cause
of issues in this repo. Reasons it's easy to miss in review:

- Each individual JS handler looks reasonable in isolation — it's only when you
  step back and see that the framework already provides the same capability that
  the duplication becomes obvious.
- The framework's idioms differ materially from the JS-native equivalents
  (e.g. `data-init` vs `addEventListener('load', …)`), so a developer working
  from JS muscle memory will reach for the wrong primitive even when they know
  Datastar exists.
- "Just one small JS file" tends to grow — every new feature adds a handler,
  and the team accumulates a parallel state-management system that has to be
  kept in sync with the server.

**Detection criteria:**
- Any new JavaScript handler that fetches a server endpoint, parses the
  response, and mutates the DOM. The Datastar idiom is `data-on:click="@post(…)"`
  on the trigger element + a server endpoint decorated with `@datastar_response`
  that yields `SSE.patch_elements` / `SSE.patch_signals`. JSON-parsing on the
  client is almost always a smell.
- Any new endpoint returning `JSONResponse` that is consumed by the browser.
  The exception is server-to-server callers (CLI hooks, webhooks like
  `/command-center/session-question`); those should be obvious. Browser-facing
  endpoints should yield SSE.
- Any new `document.getElementById(…).classList.add('open')` or
  `el.style.display = 'none'` style DOM mutation. The framework idiom is
  `data-class:open="$signalName"` or `data-show="$signalName"` driven from a
  signal that the server (or a click handler) has flipped.
- New `<script>` includes in `command_center.html` or other CC templates. The
  page should currently load only `base.js` and `cc-modals.js`. Anything beyond
  that is a regression that needs explicit justification.
- Handlers that build HTML strings in JS and inject them via `innerHTML =`. The
  framework idiom is for the server to render a Jinja fragment and yield it
  via `SSE.patch_elements(…, mode=ElementPatchMode.INNER)` into a stable
  container. Building markup in JS strings duplicates the template engine and
  bypasses autoescape.

**Examples:**

```javascript
// BAD — reinvents @post + data-show + signal patching
document.addEventListener('click', function(e) {
  const btn = e.target.closest('[data-cc-refresh]');
  if (!btn) return;
  btn.disabled = true;
  fetch('/command-center/refresh', {method: 'POST'})
    .then(r => r.json())
    .then(data => {
      showToast(data.message, data.kind);
      btn.disabled = false;
    });
});
```

```html
<!-- GOOD — declarative, server is the source of truth -->
<button id="btn-refresh"
        data-on:click="@post('/command-center/refresh')"
        data-indicator="$busyButtons.refresh"
        data-attr:disabled="$busyButtons.refresh">Refresh</button>
```

```python
# Server side
@router.post("/command-center/refresh")
@datastar_response
async def refresh_command_center(request: Request):  # noqa: ANN201
    async def _stream():  # noqa: ANN202
        try:
            await poller._poll_once()
            yield _sse_toast("Refreshed", "ok")
        except Exception as e:  # noqa: BLE001
            yield _sse_toast(str(e), "err")
    return _stream()
```

### 2. Imperative state managed in JS instead of `data-signals`

**Severity:** high

**Description:**
Whenever the page needs to remember something across user interactions — which
modal is open, which kebab is expanded, which tab is selected, what the user
typed in a search box, whether a button is in flight — the answer in this
codebase is a Datastar signal, not a JS variable, class on a DOM element, or
ad-hoc `data-attribute` mutated by JS. Reviewers should ask "where does this
state live and who owns it?" before approving any new interactive feature.

This rule catches the class of bug that produced `cc-actions.js`, `cc-drawer.js`,
and `cc-kebab.js` — each of which used DOM state (`.open` class, `data-prev-id`
attributes) as the source of truth for view-local UI state, which then had to
be kept in sync by hand at every interaction point.

**Detection criteria:**
- Any new `class.toggle('open')`, `el.dataset.foo = 'bar'`, `el.style.display = X`
  pattern in JS. The framework idiom is `$signalName = !$signalName` and
  `data-show="$signalName"` / `data-class:open="$signalName"` on the consumers.
- Code that reads state from a DOM attribute and writes it back to update the
  view. If the state existed as a signal, both reads and writes would happen
  through the same reactive channel.
- Multiple JS handlers that all need to "close all menus" / "clear all selected"
  / "reset all flags". This is a sign the state should be a single signal that
  consumers bind to — closing/clearing is then `$state = null` (or `''` — see
  rule 4) at one site.
- Per-instance JS state stored in module-level objects keyed by element id
  (e.g. `const openMenus = {}`). A scoped Datastar signal on the parent
  container will replace it.
- Modal-open booleans, tab-selected enums, accordion-expanded flags, search
  query strings — all of these are view-local state and belong on the page or
  fragment that owns them, never round-trip the server.

**Examples:**

```javascript
// BAD — DOM-as-source-of-truth, requires sync at every site
document.querySelectorAll('.strip-menu').forEach(el => el.classList.remove('open'));
document.querySelector(`.strip-menu[data-id="${id}"]`).classList.add('open');
```

```html
<!-- GOOD — one signal, every consumer reactive -->
<button data-on:click="$openKebab = $openKebab === 'card-{{ key }}' ? '' : 'card-{{ key }}'">⋯</button>
<div class="strip-menu"
     data-show="$openKebab === 'card-{{ key }}'"
     data-class:open="$openKebab === 'card-{{ key }}'"
     data-on:click__window__outside="$openKebab = ''">…</div>
```

### 3. Reaching for `data-on:<dom-event>` when the lifecycle isn't really a DOM event

**Severity:** high

**Description:**
Datastar exposes two distinct families of attributes that are often confused:

- **Event listeners**: `data-on:click`, `data-on:input`, `data-on:keydown__window__key.escape`.
  These attach a real DOM event listener and only fire when the browser fires
  that named event on the bound element.
- **Lifecycle / signal-watch attributes**: `data-init` (fires when the element
  is initialized into the DOM — page load, patch-in, attribute change),
  `data-on-signal-patch` and `data-on-signal-patch-filter` (fire on signal
  store changes). These are *attribute names* in v1, not event listeners —
  they don't go through `addEventListener`.

The recurring class of bug: a developer writes `data-on-load="@get('/events')"`
on a `<div>` to start an SSE stream. It looks reasonable. It silently does
nothing — the DOM `load` event never fires on `<div>` (only on `<body>`,
`<img>`, `<iframe>`, `<script>`, `<link>`). The right attribute is `data-init`.
Same shape: `<button data-on-load__delay.5000ms="el.remove()">` — DOM `load`
doesn't fire on `<button>` either, so the timer never starts.

**Detection criteria:**
- `data-on-load` (or `data-on:load`) on any element other than `<body>`,
  `<img>`, `<iframe>`, `<script>`, or `<link>`. This is almost always a
  mistake; the developer wanted `data-init`.
- `data-on-click`, `data-on-input`, `data-on-change` (dashed form) — these
  are legacy v0 syntax. The v1 form is `data-on:click`, `data-on:input`,
  `data-on:change` (colon). `tests/test_lint.py` blocks the dashed form;
  flag any new exception added to the allowlist.
- Bindings that try to fire "when this element appears in the DOM" using
  any DOM event other than `data-init`. There is no such DOM event; only
  `data-init` does this.
- `data-on-signal-patch` or `data-on-signal-patch-filter` placed on a small
  visually-relevant element. These should typically live on a hidden marker
  div (or `.cc-page`) so they are not coupled to a UI element's lifecycle.
- Writing custom JS to "wait for the element to be ready then run X". That's
  exactly what `data-init` does; no JS needed.

**Examples:**

```html
<!-- BAD — load event never fires on <div>; SSE connection is silently dead -->
<div class="cc-page" data-on-load="@get('/command-center/events')">…</div>

<!-- GOOD — data-init fires when the element is initialized into the DOM -->
<div class="cc-page" data-init="@get('/command-center/events')">…</div>
```

```python
# BAD — sse_helpers emits data-on-load__delay; toast never auto-removes on <div>
html = (
    f'<div id="{tid}" class="cc-toast" '
    f'data-on-load__delay.5000ms="el.remove()">…</div>'
)

# GOOD — data-init fires when the toast is patched into the DOM
html = (
    f'<div id="{tid}" class="cc-toast" '
    f'data-init__delay.5000ms="el.remove()">…</div>'
)
```

### 4. Inventing escape conventions instead of using framework-safe encoders

**Severity:** high

**Description:**
Templates in this codebase carry user-driven values (Linear identifiers, repo
names, session ids, PR titles, branch names, terminal URLs) into Datastar
attributes that are evaluated as JavaScript expressions. The naive escape
strategy (`{{ var | e }}` inside a single-quoted JS string inside a
double-quoted HTML attribute) is **not** safe — Jinja's autoescape encodes
`'` as `&#39;`, the browser decodes it back to `'` when it reads the attribute,
and the JS string closes early. This isn't theoretical: every value that flows
into a `data-on:click="@post(…, {payload: {x: '{{ x | e }}'}})"` site is one
upstream-data-shape change away from XSS.

The class of bug is: hand-rolling escape logic for a context the framework
already understands. The same applies to:

- Hand-built JSON envelopes via raw `{{ var }}` interpolation instead of
  `{{ data | tojson }}` on the whole dict (`autoescape encodes "` to `&#34;`
  which the browser decodes back, breaking JSON parse).
- Hand-built JS expressions inside `data-on:click` instead of using a
  context-aware filter (`{{ var | js_str }}` in this codebase, registered
  in `templates.py`) that escapes for both HTML-attribute and JS-string
  contexts.
- Ad-hoc string concatenation to build CSS-class lists / DOM ids when
  Datastar's `data-class:foo="$signal"` and stable server-rendered ids
  would do the same job.
- Building Datastar signal *paths* by concatenation without sanitizing the
  components for valid JS identifier syntax. `$busyButtons.launch_BAK-1234`
  is parsed as `($busyButtons.launch_BAK) - (1234)` — valid JS, wrong
  semantics. The repo's `_to_signal_key()` / `signal_key` model property is
  the canonical sanitizer; any new code that builds a signal name from a
  user identifier without going through that function is a candidate bug.

**Detection criteria:**
- New `'{{ var | e }}'` patterns inside any `data-on:*` attribute. Use
  `{{ var | js_str }}` (context-aware filter) or `{{ var | tojson }}` on the
  whole payload dict.
- New `data-signals='{"key": "{{ var }}", …}'` patterns where `var` is
  interpolated into a literal JSON string. Build the dict server-side and
  use `data-signals='{{ env_dict | tojson }}'`.
- New `$signalName` or `$obj.subkey` references where `signalName`/`subkey`
  is built from a runtime identifier (card key, session id, ticket id) without
  going through `signal_key` / `_to_signal_key`.
- Any `markupsafe.Markup(f"<button>…")` or hand-built HTML strings in Python
  that interpolate untrusted input. The framework idiom is to render a Jinja
  fragment via `render(…)` so autoescape applies.
- New tests that assert escape behavior via substring matching only (e.g.
  `assertIn('cc-toast-err', result)`) without parsing the resulting HTML to
  verify attribute boundaries are well-formed.

**Examples:**

```jinja
<!-- BAD — | e doesn't escape for the JS-string-in-HTML-attribute context -->
<button data-on:click="@post('/foo', {payload: {key: '{{ user_input | e }}'}})">

<!-- GOOD — js_str (custom filter in templates.py) escapes for both contexts -->
<button data-on:click="@post('/foo', {payload: {key: {{ user_input | js_str }}}})">

<!-- GOOD — let tojson handle the whole envelope -->
<div data-signals='{{ {"sessionId": session.session_id, "stepId": step.step_id} | tojson }}'>
```

```python
# BAD — string concat builds an unparseable signal name for hyphenated keys
data_indicator = f"$busyButtons.launch_{card.key}"  # → 'launch_BAK-1234' = subtraction

# GOOD — signal_key sanitizes to [A-Za-z0-9_]
data_indicator = f"$busyButtons.launch_{card.signal_key}"  # → 'launch_BAK_1234'
```

### 5. Inlining variant markup 4× / 22× instead of factoring a Jinja macro

**Severity:** medium

**Description:**
When the same UI primitive renders in many contexts (a launch button across
strip / kebab / footer; a kebab toggle across cards / management tray; a
queue-item row across drawer fragments; a triage button per finding), the
template tends to inline the markup at every site instead of factoring a
single Jinja macro / partial / `{% include %}`. The structural shape never
varies — only the contextual labels, payload fields, and class hooks do —
which is exactly what macros are for.

Why this is the *class* behind several specific findings: every inline copy
becomes a place where a future change has to be applied, and each copy that
gets missed is a latent bug. The Datastar refactor introduced
`fragments/launch_button.html` as a server-side snapshot template, but
`kanban_card.html` still inlined the launch-button markup 22 times — with the
result that the snapshot rendered different markup than the on-page button,
and a Step-13 bugfix (per-card busyButton pre-init) only got applied to one
of the variants.

Catching this class via "is this inlined more than ~3 times" rather than
listing specific symptoms keeps the rule from going stale as new components
are added.

**Detection criteria:**
- New duplicated blocks in templates: ≥3 inline copies of structurally
  identical markup that differ only in label / payload / class hooks.
  Factor into a `{% macro %}` in a `_*.html` partial in the same directory.
- New helper fragment files (`fragments/X.html`) that are referenced by
  exactly one server callsite and zero templates. Either inline back into
  that one callsite, or extend it via `{% include %}` from the templates
  that need the same markup.
- Repeated `{% if step.step_name == 'plan' %}…{% elif … %}` or similar
  type-to-class lookups that appear in >1 template. The repo's
  `_drawer_helpers.html` (`step_icon`, `queue_item`) is the canonical
  pattern for these.
- Per-button data-on:click expressions that exceed ~80 characters or include
  multi-statement JS (`@post(…); $openKebab = ''; …`). This is a sign the
  call site is doing too much; consider a macro or a named JS dispatch
  function (see rule 6).

### 6. Browser-API-only JS dispatched inline instead of via named functions

**Severity:** medium

**Description:**
Some interactions genuinely require JavaScript — clipboard writes, `iframe`
lifecycle, `Notification.requestPermission()`. The framework explicitly does
not handle these; reaching for JS is correct. But where the JS lives matters:

- **Inline `data-on:click="navigator.clipboard.writeText(…); window.open(…); …"`**
  scatters the browser-API call across dozens of templates. Every site has
  to be kept in sync; refactoring the underlying behavior touches every site.
- **Named dispatch functions** (`window.dispatchOpenTerminal(url)`,
  `window.dispatchCopyStandup(html, markdown)`) declared in a small JS file
  centralize the browser-API call in one location. Templates call the
  dispatcher, which fires a `CustomEvent` that a single listener handles.
  Refactors and bug fixes apply at one site.

This rule catches the *class* of problem behind the standup-copy and
terminal-iframe findings: even when JS is the right answer, structuring it
as inline expressions invites the same drift problem as inlining template
markup (rule 5).

**Detection criteria:**
- New `data-on:click="<browser-api>(…)"` inline expressions where
  `<browser-api>` is `navigator.clipboard.writeText`, `window.open`,
  `Notification.requestPermission`, `document.dispatchEvent(new CustomEvent(…))`,
  or any other browser API. Two or three such call sites is fine; >3 is a
  smell.
- New JS files beyond `base.js` and `cc-modals.js`. Any new browser-API
  helper should live in `cc-modals.js` (or extend it minimally), and the
  template should call a named `window.dispatchX(…)` function rather than
  inlining the API call.
- Multiple paths that close / clean up the same browser-API resource
  (e.g. iframe). The IIFE that owns the resource should be the only place
  that knows how to release it; signal-driven close watchers should call
  the IIFE's exposed `.close()` method rather than dispatching a separate
  `CustomEvent` that re-implements teardown. (This is the class behind the
  terminal-modal closure-leak finding.)
- New `addEventListener` calls in JS files. Every listener is a place
  where state can desync if the dispatch path changes; prefer fewer
  listeners with broader responsibility over many narrow listeners.

**Examples:**

```html
<!-- BAD — inlined API call repeated at every kebab copy button -->
<button data-on:click="navigator.clipboard.writeText({{ cmd | tojson }}); $openKebab = ''">Copy</button>
<!-- (×20 across kanban_card.html) -->

<!-- GOOD — single dispatch site, JS owns the API call -->
<button data-on:click="dispatchCopyCmd({{ cmd | tojson }}); $openKebab = ''">Copy</button>
```

```javascript
// cc-modals.js — one place that knows how clipboard works
window.dispatchCopyCmd = function(cmd) {
  navigator.clipboard.writeText(cmd).catch(/* error UI */);
};
```

### 7. Server endpoints whose contract differs from the verb / response style

**Severity:** medium

**Description:**
HTTP semantics carry implicit contracts that infrastructure outside the app
relies on: GETs are idempotent and cacheable; POSTs aren't; status codes
indicate categorical outcome (200 OK vs 404 vs 500). When an endpoint's
behavior diverges from these expectations, things downstream break in
ways the unit tests won't catch.

In this codebase, the recurring class is endpoints that switched from one
contract to another mid-life and didn't get re-aligned:

- A `GET` endpoint that returned one-shot HTML and now yields SSE patches
  is technically still valid HTTP but breaks any caching layer (CDN,
  reverse proxy) that cached its response.
- An endpoint that returned `JSONResponse` with `4xx`/`5xx` status codes
  for errors and now yields SSE always-200 with errors-as-toasts loses
  the distinction in access-log monitoring.
- An endpoint reachable by both browser and external CLI/webhook callers
  whose response shape is now Datastar-specific breaks the non-browser
  caller silently.

Reviewers should ask: "What contract did this endpoint promise, and what
contract does it deliver now?" — and verify the two match for every caller
class (browser, CLI, webhook, monitoring, cache).

**Detection criteria:**
- New `@datastar_response` on a `@router.get` route. SSE streams over GET
  are an HTTP smell; check whether any caching/CORS layer is in scope and
  whether the endpoint should be POST.
- New conversion of an endpoint from `JSONResponse` to `@datastar_response`
  that drops distinct error status codes. Verify ops monitoring isn't
  scraping `5xx` from access logs for this endpoint; consider keeping a
  `logger.error(...)` with a stable `event=` field for log-based alerting.
- New endpoint that is *not* decorated with `@datastar_response` but is
  called via Datastar's `@post(…)` from a template. The browser will
  parse the response as JSON and apply Datastar resync semantics that
  may not match the response shape — frequently breaks signal state
  silently.
- Endpoints intended for non-browser callers (CLI hooks, webhooks) that
  start yielding SSE. The whitelist should be obvious in the route file
  (a comment naming the caller); without it, a future SSE conversion
  silently breaks the external caller.
- Any endpoint that catches `except Exception` and yields the raw
  `str(e)` in the user-facing toast. Tighten to a typed allowlist
  (e.g. `(LaunchError, OSError, subprocess.CalledProcessError)`) so
  programming errors don't surface stack traces in the UI.

**Examples:**

```python
# BAD — GET + SSE breaks any caching layer that respects HTTP semantics
@router.get("/command-center/drawer/{session_id}")
@datastar_response
async def get_drawer(session_id: str, request: Request):  # noqa: ANN201
    async def _stream():  # noqa: ANN202
        yield SSE.patch_elements(html, selector="#review-drawer-container",
                                 mode=ElementPatchMode.INNER)
        yield SSE.patch_signals({"modals": {"drawer": True}})
    return _stream()

# GOOD — POST aligns with the new contract
@router.post("/command-center/drawer/{session_id}")
@datastar_response
async def get_drawer(session_id: str, request: Request):  # noqa: ANN201
    …
```

```python
# BAD — except Exception surfaces programming errors in the toast
try:
    rollback_worktree(session.worktree_path)
except Exception as e:  # noqa: BLE001
    yield _sse_toast(str(e), "err")  # KeyError, AttributeError leak through

# GOOD — typed allowlist; programming errors propagate as 500-equivalents
try:
    rollback_worktree(session.worktree_path)
except (LaunchError, OSError, subprocess.CalledProcessError) as e:
    logger.exception("cleanup-worktree failed")
    yield _sse_toast(str(e), "err")
```

### 8. Defensive guards added without addressing why the invariant was violated

**Severity:** medium

**Description:**
When a bug surfaces with "this signal is undefined / null / wrong type", the
reviewer's first question should be *why* the value is in that state, not
"what guard fixes the symptom". Datastar v1 has several traps that look like
they want defensive guards but actually want a different upstream choice:

- `data-indicator="$busyButtons.X"` defaults the named signal to `true` if it
  doesn't exist in the signal store. The naive fix is "add a guard in JS to
  flip it false". The right fix is to pre-initialize every signal the page
  will reference in the `data-signals` envelope at render time (computed
  server-side from the data the page renders).
- Setting a signal to `null` (e.g. `$openKebab = null`) deletes it from the
  signal proxy *without* firing reactive notifications. Watchers
  (`data-class`, `data-show`) miss the change. The naive fix is "add a
  watcher with a different filter". The right fix is to use `""` or `false`
  as the unset value so the signal stays in the store and notifications
  fire.
- `data-bind="$signalName"` does not work — `data-bind` takes a signal
  *path* (`signalName`), not a `$`-prefixed expression. The naive fix is
  "wire up an extra `data-on:input` to sync the value". The right fix is
  to drop the `$`.
- A response from the server arrives in a shape Datastar resyncs from
  (e.g. plain JSON instead of SSE patches). The naive fix is "have JS
  intercept the response and re-set signals after". The right fix is to
  decorate the endpoint with `@datastar_response` and yield
  `SSE.patch_signals(...)` so the server is the source of truth.

**Detection criteria:**
- New JS code that "fixes" a signal/state issue by writing to the DOM or
  re-firing an event after a server response. Audit whether the response
  shape (SSE vs JSON) is the actual problem.
- New `if (!$signal) $signal = …` patterns in templates. The signal
  should be initialized in the parent's `data-signals` envelope.
- New "watcher" attributes added because a signal change isn't propagating.
  Check whether the signal is being set to `null` (deletes it from the
  proxy without notifying watchers).
- New JS or template logic that special-cases the empty/missing/uninitialized
  state of a signal in multiple places. The signal should have a defined
  default value at one site (the page envelope or the fragment that owns
  the state) and consumers should bind without guards.
- Try/except blocks added around a render call to catch a "template
  variable not defined" error. The variable should be passed in
  `build_*_context` or set as a default in the template.

**Examples:**

```javascript
// BAD — guard masks the real bug (signal was deleted by null assignment)
if ($openKebab === undefined) {
  $openKebab = '';  // re-create the signal so watchers fire
}

// GOOD — never delete the signal in the first place
$openKebab = $openKebab === 'card-X' ? '' : 'card-X';
//                                       ^^ '' keeps the signal in the store
```

```jinja
<!-- BAD — per-card guard for an uninitialized indicator -->
<button data-indicator="$busyButtons.kill_{{ id }} || false">Kill</button>

<!-- GOOD — pre-initialize the signal at page-render time -->
<!-- in command_center.html data-signals envelope: -->
"busyButtons": {{ {f"kill_{s.signal_key}": False for s in sessions} | tojson }}
<!-- then the button binds without a guard -->
<button data-indicator="$busyButtons.kill_{{ session.signal_key }}">Kill</button>
```
